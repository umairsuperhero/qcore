## Mission
Turn QCore from "a core you run" into "a tool in your dev loop." Today the built-in
simulator runs named error injections (`wrong_ki`, `wrong_plmn`, …) and even a **one-off**
custom YAML scenario (`POST /api/simulator/custom`) — but a user **cannot author, save,
list, and re-run their own scenarios with a deterministic pass/fail result.** Build that: a
user defines a scenario (YAML or UI), saves it, runs it against the simulator, and gets a
**deterministic PASS/FAIL + the live trace.** This is the foundation for P3.2 (CI hooks).

## What already exists — REUSE, don't rebuild
1. **`pkg/simulator/scenario.go`** — `ScenarioDefinition{ Name, Description, Mode,
   Overrides{ MMEAddr, PLMN, TAC, IMSI, Ki, OPc } }`, plus `LoadScenario(io.Reader)` (YAML),
   `LoadScenarioFile(path)`, and `Apply(*Options)`. **Extend this; don't replace it.**
2. **`pkg/dashboard/simulator.go`** — `SimulatorController.RunCustom(*simulator.
   ScenarioDefinition)`, `handleSimulatorCustom` (`POST /api/simulator/custom` runs a
   one-off custom scenario), and `SimulatorStatus{ State: idle|running|success|failed,
   LastJourney, LastError, FailedStep, Mode, LastScenario }`. The run + terminal-status
   machinery already exists — reuse it for the runner.
3. **`pkg/diag`** Cause tags (e.g. `wrong_ki`/`unknown_subscriber`/`plmn_mismatch`/…) —
   use these as the vocabulary for a scenario's EXPECTED failure cause.
4. **Dashboard simulator + Live-Trace UI** on the real `/api/events/stream` SSE +
   diagnostics — reuse to show a scenario run's trace + result.

## The unit of work
1. **Inspect the four items above first** so you build on them.
2. **Declare expected outcome.** Extend `ScenarioDefinition` with an optional `Expect`:
   ```yaml
   expect:
     result: success         # or "failure"
     cause: wrong_ki         # optional diag Cause tag when result: failure
     failed_step: ""         # optional
   ```
   Keep it **back-compat**: existing custom scenarios without `expect` still run and report
   the raw outcome (pass/fail = null).
3. **Persistence (small + simple).** A scenario store: save / get / list / delete named
   scenarios as YAML files under a config-driven dir (default e.g. `scenarios/` or the
   dashboard data dir). **No DB.** Validate names (reject path traversal / weird chars).
4. **Runner with deterministic pass/fail.** Given a saved scenario, run it via the existing
   `RunCustom`/controller, wait for the terminal `SimulatorStatus` (success/failed), then
   compare actual vs `Expect` → `{ pass: bool, expected, actual, journeyId, failedStep }`.
   No `Expect` → return the raw outcome with `pass: null`.
5. **Endpoints** (register in `pkg/dashboard/server.go` near the simulator routes):
   - `GET /api/scenarios` — list (name, description, mode, expect).
   - `POST /api/scenarios` — save (YAML or JSON body).
   - `GET /api/scenarios/{name}` — fetch one.
   - `DELETE /api/scenarios/{name}`.
   - `POST /api/scenarios/{name}/run` — run + return the pass/fail result (incl. journeyId
     so the UI links to the trace).
6. **Dashboard UI (scoped):** a "Scenarios" panel — list saved scenarios, create/edit (YAML
   textarea or a small form: name, mode, overrides, expect), **Save**, **Run** → PASS/FAIL
   badge + a link to the Live Trace for that journey. Reuse existing card/trace styling;
   one panel in the existing simulator/RAN area is fine — no new top-level tab needed.

## Tests
- Go: scenario store CRUD (save/list/get/delete, name validation, malformed YAML); the
  pass/fail comparison (success-expected-and-got; failure-expected-with-matching-cause;
  mismatch → fail; no-expect → raw); the run endpoint (with a mocked controller/status).
  Mirror existing `pkg/dashboard/*_test.go` and `pkg/simulator/*_test.go` styles.
- Frontend: `tsc --noEmit` clean; the panel lists / saves / runs.
- **Preserve all existing tests.**

## Acceptance / Definition of done
- A user can author a scenario (YAML or UI), save it, see it listed, run it, and get a
  deterministic PASS/FAIL + a link to the live trace.
- A scenario expecting `failure: wrong_ki` PASSES when the injected attach fails with that
  cause and FAILS if the outcome differs; a happy-path scenario PASSES on success.
- `go build ./... && go vet ./... && go test -race ./...` green in `golang:1.23`; frontend
  `tsc` + `vite build` green; `make verify-fast` green.
- Dashboard runtime check: save + run a `wrong_ki` scenario and a happy-path scenario; both
  report the right PASS/FAIL.
- Docs reconciled honestly: README (Phase D / scenario authoring row), `docs/audit-v1.0.md`
  revision entry, `docs/next-phases-plan.md` P3.1 → done. Mark ✅ only after the above.
